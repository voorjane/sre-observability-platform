## Обзор сервиса

Клиент создаёт заказ запросом `POST /api/v1/orders`. Сервис order-api проверяет входные данные и синхронно вызывает `POST /internal/process` в payment-worker. При успешном платеже order-api возвращает `201`, `status=COMPLETED` и `payment_status=PROCESSED`.

SLO использует 30-дневное скользящее окно

## SLIs и SLOs

| Категория | SLI | SLO |
|---|---|---|
| **API** |
| Доступность | Доля учитываемых ответов без `5xx`. Источник — счетчик `http_requests_total` order-api. | **Не менее 99.9%** |
| Задержка | `p95` длительности запросов, включая `5xx`. Источник — `http_request_duration_seconds_bucket` order-api. | **p95 < 250 ms** |

Для доступности `201` является хорошим событием, `500/502/503` — плохими. `4xx` исключаются из обоих SLI, а их объём показывается отдельно. `/healthz`, `/metrics`, неизвестные пути и методы не относятся к операции заказа. Ошибка worker и следующий за ней `502/503` order-api дают одно плохое событие.

## Обоснование целей

**99.9%** и **250 ms** выбраны как целевые значения проекта. В репозитории пока нет результатов нагрузочных прогонов и подтверждения полного 30-дневного окна, которые обосновывали бы достижимость этих значений под штатной нагрузкой.

## Бюджет ошибок

Для доступности допустимая доля ошибок равна **0.1%** учитываемых запросов:

```text
allowed_errors   = 0.001 × N
remaining_errors = 0.001 × N − E
budget_remaining = 1 − (E / N) / 0.001, при N > 0
```

Пример: при `N = 20 000` допустимы `20` ошибок. Если наблюдалось `E = 24`, доступность составляет `99.88%`, остаток равен `−4` ошибкам или `−20%` бюджета. При `E = 20` цель достигается ровно на границе, остаток бюджета — `0`.
